1. CORS & the Browser

The single most common "explain how it works" question for a full-stack role, because it sits exactly on the seam between frontend and backend.

Q1 What is CORS?

A browser security mechanism. By default the browser will not let JavaScript on one origin read a response from a different origin. CORS is how a server says "these specific origins are allowed to read my responses" — by sending particular response headers. The cors npm package just sets those headers for you.

The point that gets you the mark CORS is enforced by the browser, not the server. Postman and curl ignore it completely. It is not a server-side protection.

Q2 What exactly is an "origin"?

Scheme + host + port. All three must match. http://localhost:3000 and http://localhost:8000 are different origins because the port differs — which is exactly why a local Next frontend talking to a local Express backend needs CORS at all. http:// vs https:// also differs.

Q3 What does the same-origin policy actually block?

Not the sending. For a "simple" request the browser sends it, the server runs the handler, and the response comes back — the browser then refuses to hand it to JavaScript. So the side effect already happened. This is why CORS is not a substitute for authentication.

Q4 What is a preflight request?

For requests that aren't "simple", the browser sends an OPTIONS request first to ask permission, carrying Access-Control-Request-Method and Access-Control-Request-Headers. If the server's reply allows it, the browser then sends the real request. If not, the real request is never sent at all.

Q5 When does a preflight happen?

Whenever the request isn't simple. Simple means: method is GET, HEAD or POST; only safe headers; and Content-Type is one of text/plain, multipart/form-data, application/x-www-form-urlencoded.

So sending JSON (application/json) triggers a preflight. So does any custom header, or PUT/PATCH/DELETE. In practice almost every API call in a real app is preflighted.

Q6 Why is preflight necessary if the browser could just check afterwards?

Because some requests have side effects. A DELETE that reaches the server has already deleted something — blocking the response afterwards is too late. Preflight asks before anything happens, so a disallowed request never runs.

Q7 Which headers does the browser check, and who sends them?

The server sends them; the browser reads and enforces them.

  • Access-Control-Allow-Origin — which origin may read the response
  • Access-Control-Allow-Credentials: true — cookies are permitted
  • Access-Control-Allow-Methods / -Headers — the answers to a preflight
  • Access-Control-Max-Age — how long the browser may cache the preflight result

Q8 What does credentials do, and why are there two halves?

Cookies are not sent cross-origin by default. Enabling them needs agreement from both sides:

  • Frontend — withCredentials: true tells the browser to attach cookies to the request.
  • Backend — credentials: true in the cors options sets Access-Control-Allow-Credentials: true, telling the browser it may hand the response to JS.

Miss either one and cookies silently do nothing — no error, just an unauthenticated request.

Q9 Why can't you use origin: "*" together with credentials?

The spec forbids it, and the browser rejects the response. * means "any website", and "any website, and send the user's cookies too" would let a malicious page make fully authenticated requests as the logged-in user. With credentials you must name the exact origin.

app.use(cors({
  origin: process.env.CORS_ORIGIN ?? "http://localhost:3000",
  credentials: true
}));

Q10 So does CORS protect my server?

No. It protects users of other websites from having their browser used against your API. Your server itself is unprotected — anything that isn't a browser ignores CORS entirely. Real protection is authentication and authorization.

2. Cookies & Session Security

Where XSS and CSRF questions always land.

Q11 What does cookieParser() do?

Cookies arrive as one string header: Cookie: accessToken=abc; refreshToken=xyz. cookie-parser splits that into an object on req.cookies. Without it, req.cookies is undefined and every auth check silently fails.

Q12 What does each cookie flag protect against?

  • httpOnly: true — JavaScript cannot read the cookie via document.cookie. Limits XSS token theft.
  • secure: true — only sent over HTTPS. Stops network sniffing.
  • sameSite: "strict" — not attached to requests started by another site. Stops CSRF.
const cookieOptions = {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "strict"
};

Q13 XSS vs CSRF — what's the difference?

  • XSS — the attacker gets their JavaScript running on your page. They can then do anything the user can, and read anything the page can.
  • CSRF — the attacker's site causes the user's browser to send a request to your site, relying on the cookie being attached automatically. They cannot read the response, but the side effect already happened.

Short version: XSS is code running where it shouldn't. CSRF is a request being sent from where it shouldn't.

Q14 How is this app protected from each?

XSS: tokens are in httpOnly cookies, so injected script can't read them. React also escapes rendered values by default.

CSRF: sameSite: "strict" means the browser won't attach our cookies to a request initiated by another origin.

Be honest about this httpOnly does not prevent XSS — it limits the damage. An attacker with script execution can still make requests as the user; they just can't steal the token to use elsewhere.

Q15 Why store the JWT in an httpOnly cookie instead of localStorage?

localStorage is readable by any JavaScript on the page — one XSS and the token is exfiltrated. httpOnly cookies are invisible to JS. The trade-off is that cookies are sent automatically, which introduces CSRF risk, and that's what sameSite handles. Cookies also mean you never manage an Authorization header by hand.

Q16 Why does the access cookie deliberately outlive the access token?

This is a subtle one and a good answer to have ready.

If the cookie expired at the same moment as the token, the browser would simply stop sending it. jwt.verify would never run, so we'd never get a TokenExpiredError — we'd get "no token at all" instead, and the refresh flow would never trigger.

Letting the cookie live as long as the refresh token makes the JWT's own exp the single thing that decides. One source of truth for expiry.

const REFRESH_COOKIE_MAX_AGE = durationToMs(process.env.REFRESH_TOKEN_EXPIRY, 7*24*60*60*1000);
const ACCESS_COOKIE_MAX_AGE  = REFRESH_COOKIE_MAX_AGE;   // intentionally the same

Q17 What must clearCookie match?

The same path, domain, sameSite and secure values used when the cookie was set. If they differ the browser keeps the old cookie and you get the very confusing "logged out but still logged in" state.

Q18 Why does logout need a server call at all?

Two reasons. Only the server can invalidate the stored refresh token, and only a server response can clear an httpOnly cookie — JavaScript can't touch it. Clearing React state alone would leave a fully working session sitting on disk.

Q19 What if the logout request itself fails?

Clear the local state anyway. The user asked to leave and the UI must reflect that. Surface the failure, but never trap someone in a logged-in interface because a network call didn't land.

try   { await api.post("/user/logout"); }
catch { toast.error("Could not reach server, logged out locally"); }
finally { setLoggedInUserDetails(null); }   // always

3. Request Body Parsing

Q20 express.json() vs express.urlencoded() — what does each convert?

  • express.json() handles Content-Type: application/json. Body arrives as the raw text {"email":"a@b.com"}; it parses that into an object.
  • express.urlencoded() handles application/x-www-form-urlencoded. Body arrives as email=a%40b.com&age=20; it parses that into an object. This is what a plain HTML <form> sends.

Each only touches its own content type. The wrong parser does nothing at all — silently.

Bug I actually shipped I registered express.json() twice instead of adding express.urlencoded(). Form posts arrived with req.body undefined and nothing anywhere said why.

Q21 What does extended: true mean?

Which library parses the query-string syntax. false uses Node's querystring — flat key/value only. true uses qs, which supports nesting and arrays, so user[name]=Ali&tags[]=a&tags[]=b becomes a real nested object.

Q22 Why limit: "16kb"?

A cap on body size. Without it, someone can POST a huge payload and exhaust server memory — a cheap denial-of-service. 16kb is plenty for JSON forms. File uploads should not go through this at all; they belong in a streaming parser like multer.

Q23 In Express 5, what is req.body when there's no body?

undefined, not {}. Express 4 gave you an empty object. So const { email } = req.body now throws instead of quietly giving you undefined. Guard with req.body ?? {}, or make sure the parser actually ran for that content type.

4. Passwords & bcrypt

Q24 If the salt is random, how does bcrypt compare a password later?

The salt isn't secret and isn't stored separately — it's embedded in the hash string. A bcrypt hash looks like:

$2b$10$N9qo8uLOickgx2ZMRZoMye.IjZAgcfl7p92ldGxad68LJZdL17lhW
 |   |  |                     |
 |   |  22-char salt          the actual digest
 |   cost factor (10)
 algorithm version

bcrypt.compare reads the cost and salt back out of the stored hash, hashes the incoming password exactly the same way, and compares the results.

Q25 What are salt rounds?

The cost factor. Work is 2^rounds, so 10 means 1024 iterations of the key setup, and every +1 doubles the time. It's deliberately slow so that brute-forcing a stolen database of hashes is expensive. You raise it as hardware gets faster.

Q26 Why hash in a pre('save') hook instead of in the controller?

So it can't be forgotten. Signup, password reset, an admin creating a user, a seed script — all of them go through save(), so all of them get hashing. Put it in one controller and the next controller you write leaks plaintext.

It's the model's job to know how a password is stored. The controller shouldn't have an opinion.

Q27 Why the isModified guard?

userSchema.pre("save", async function () {
  if (!this.isModified("password")) return;
  this.password = await bcrypt.hash(this.password, 10);
});

Every save() runs the hook. On login we save the user again to store a new refresh token — without the guard we'd hash the already hashed password, and the user could never log in again. It's a real, silent, account-destroying bug.

Q28 Why is verifyPassword a schema method rather than bcrypt in the controller?

The model owns how a password is checked. The controller just asks "is this correct?". If the algorithm ever changes — bcrypt to argon2, say — one file changes instead of every login path.

5. JWT & the Auth Flow

The centre of gravity for this project. Expect the whole section as one long conversation.

Q29 What is a JWT?

Three base64url-encoded parts joined by dots: header.payload.signature. The header names the algorithm, the payload holds claims (we put _id, email, name, plus iat and exp), and the signature is an HMAC of the first two parts using a server-side secret.

Q30 Is a JWT encrypted?

No — it's signed, not encrypted. Anyone holding the token can base64-decode the payload and read it. Never put anything secret in there. The signature only proves the token wasn't altered and came from someone holding the secret.

Common trap Interviewers love asking this because so many candidates say "encrypted". Say signed, and say why it matters: no passwords, no PII beyond what's already public to that user.

Q31 Why two tokens instead of one?

It's a trade-off between exposure and convenience.

  • Access token — short-lived (15m), sent on every request. Highly exposed, but if stolen it dies quickly.
  • Refresh token — long-lived (7d), used only to mint new access tokens. Rarely exposed, and it's stored in the DB so it can be revoked.

A single long-lived token would be the worst of both: constantly exposed and impossible to revoke.

Q32 JWTs are stateless — so how do you log someone out?

You can't invalidate an access token that's already issued. That's the genuine cost of statelessness. Instead you keep it short-lived and revoke the refresh token by clearing it from the user document. Once the access token expires — minutes later — the session is really dead.

If you need instant revocation, you're back to server-side sessions or a token denylist, and you've given up statelessness.

Q33 What is refresh token rotation and why do it?

Every time a refresh token is used it is consumed, and a brand-new one is issued and saved. The old one is immediately invalid.

Two benefits: a stolen refresh token is only useful until the real user next refreshes, and if both the attacker and the user try to use the same token, one of them fails — which is a detectable signal that something is wrong.

Q34 Walk me through your login flow.

  1. POST /login with email and password
  2. Find the user with .select('+password') — the field is select: false by default
  3. bcrypt.compare, via the schema's verifyPassword method
  4. Generate access + refresh tokens from schema methods
  5. Store the refresh token on the user document
  6. Set both as httpOnly cookies and return the user object

No token ever appears in the JSON body. Cookies only.

Q35 What happens when the access token expires?

  1. Protected request → verifyJWT → jwt.verify throws TokenExpiredError
  2. Middleware converts that to a 401 carrying code: "TOKEN_EXPIRED"
  3. The axios response interceptor sees the code, calls /refresh-token once, then replays the original request
  4. The user sees nothing at all

Q36 Why refresh only on TOKEN_EXPIRED and not on INVALID_TOKEN?

Expired means the token was genuinely ours and simply aged out — refreshing is the correct response. Invalid means it was tampered with or signed with a different secret; refreshing can't fix that and just wastes a round trip before failing anyway.

Say this part out loud Branch on a machine-readable code, never on the message text. You will reword a message one day and silently break the client.

Q37 What is original._retried for?

original is error.config — the config of the request that failed. _retried is our own flag, not an axios property; the underscore is convention for "mine, added on". It marks "this request has already been through the refresh path".

Without it, if the replayed request also 401s, the interceptor refreshes again, and again, forever. It's a one-attempt guard.

!original._retried reads as "hasn't been retried yet" — on the first pass the property doesn't exist, so !undefined is true.

Q38 Why is there a single shared refresh promise?

Because a page load fires several requests at once. If /me, /products and /cart all 401 together, you'd send three refresh calls. With rotation, the first rotates the token and the other two arrive holding an already-consumed one — so they fail and log the user out.

let refreshPromise = null;

const refreshSession = () => {
  if (!refreshPromise) {
    refreshPromise = axios.post(url, {}, { withCredentials: true })
                          .finally(() => { refreshPromise = null; });
  }
  return refreshPromise;
};

All three await the same promise, so exactly one refresh happens; then each replays its own original request. .finally clears the slot so the next expiry starts fresh.

Q39 Tell me about a bug you debugged.

The infinite refresh loop. The app would sit on the login page reloading forever.

The refresh controller correctly returned 401 when the refresh token was dead — but it never sent Set-Cookie. So the dead cookies stayed in the browser. Every reload ran the identical cycle: /me → 401 → refresh → 401 → redirect to /login → /me again.

My first hypothesis was wrong — I blamed the NO_TOKEN branch. The evidence killed it: removing that branch didn't stop the loop. Which meant the cause had to be state that survived across reloads, and the only such state was the cookies.

catch (error) {
  // the session is unrecoverable — remove the cookies so the next
  // page load starts clean instead of repeating a doomed request
  res.clearCookie("accessToken", cookieOptions)
     .clearCookie("refreshToken", cookieOptions);
  ...
}
The transferable lesson An auth failure must leave the client in a changed state. If nothing changes, retrying is guaranteed to repeat — that's the definition of a loop.

Q40 Is clearing cookies on refresh failure standard practice?

Yes. If the refresh token is expired, invalid or revoked, the session is unrecoverable — there is no path back except logging in. Leaving the cookies in place guarantees the client repeats a doomed request on every page load and hammers your server. Clear them.

Q41 Why a code field on your errors?

The message is for humans and will get reworded. A code is a contract the frontend can rely on. Our ApiError takes (statusCode, message, code) and the handler only forwards the code when it's a string — because Mongo's duplicate-key code is the number 11000, and the client must never try to branch on that.

Q42 Where's the remaining CSRF risk, and what covers it?

Cookies attach automatically, so in principle a malicious site could trigger a state-changing request. sameSite: "strict" stops the browser attaching our cookies to cross-site-initiated requests, which covers it here.

For production across subdomains, or where you need sameSite: "none", you add a CSRF token — a value the server issues that the client must echo in a header, which an attacker's site can't read.

6. Mongoose & MongoDB

Q43 What is MongoDB, and what is Mongoose?

MongoDB is the database — document-oriented, storing BSON documents inside collections, schema-less by default.

Mongoose is an ODM (Object Document Mapper) — a Node library on top of the MongoDB driver that adds schemas, validation, type casting, middleware hooks, and a friendlier query API. The schema lives in your app, not in the database.

Q44 Schema vs Model vs Document?

  • Schema — the shape and the rules
  • Model — the class compiled from the schema; you query through it (User.findOne())
  • Document — one record, one instance (const user = await User.findById(id))

Q45 What are .pre(), .methods, .statics and .set() called?

  • .pre() / .post() — middleware (also called hooks)
  • .methods — instance methods, live on a document: user.verifyPassword()
  • .statics — static methods, live on the model: User.findByEmail()
  • .set() — schema options
  • .virtual() — virtuals, computed fields never stored in the DB

Q46 Instance method or static — how do you choose?

Instance if it needs this document's data (verify this user's password, generate this user's token). Static if it operates on the collection (find a user by email).

Rule of thumb: if you find yourself passing the document in as an argument to a static, it should have been an instance method.

Q47 You set select: false on password — why did the API still return it?

Because select: false only applies to queries. User.create() returns the document you just built in memory — nothing was queried, so nothing was excluded.

That's why the toJSON transform exists: it strips the field on the way out, regardless of how the document was produced.

Q48 What does the toJSON transform actually do?

userSchema.set("toJSON", {
  transform: (doc, ret) => {
    delete ret.password;
    delete ret.refreshToken;
    delete ret.__v;
    return ret;
  }
});

The chain is worth being able to recite: res.json(user) calls JSON.stringify(user). JSON.stringify checks whether the object has a toJSON() method and, if so, stringifies that method's return value instead. Mongoose implements toJSON, and your transform edits the plain object it builds. The document in memory is untouched — only the output changes.

Q49 Then what is select: false still doing?

Defence in depth at a different layer. It keeps the hash out of query results entirely — not sitting in memory in every controller, not caught by an accidental console.log, not spread into another object.

toJSON guards the response. select: false guards everything else. That's also why login must explicitly opt back in with .select('+password').

Q50 So Mongoose "automatically knows" to strip those fields?

Not automatically — it does it because you configured toJSON. Nothing is magic. res.json serialises, serialising consults toJSON, and toJSON is where your rule lives.

Q51 Why does an object have to be "serialized" to travel over a network?

A network carries bytes. A JavaScript object exists in memory as references and pointers, which mean nothing to another process on another machine.

Serializing means flattening it into a byte sequence in an agreed format — JSON text here. The receiver parses those bytes back into its own object. The two objects are copies, not the same thing.

Q52 "So only text can travel over the network?"

Only bytes can. Text is one way of encoding bytes, and JSON is a text format, so JSON travels as UTF-8 bytes. Images, video and file uploads travel as bytes too — just not text-shaped ones. The rule is: bytes on the wire, structure agreed by convention on both ends.

Q53 Why did you remove next from the async pre-save hook?

Mongoose supports two styles, and they're alternatives, not partners:

  • Callback hook — you signal "done" with next() and "failed" with next(error).
  • Async hook — the returned promise is the signal. Return to continue, throw to abort.

When the hook is declared async, Mongoose watches the promise and never passes next at all — so the parameter is undefined and calling it is a TypeError. My function was already async, so the promise was always the real channel; the next calls were a second, broken mechanism layered on top.

Why it looked like it worked The broken branch only ran on the second save — the login path, which saves the user to store a refresh token. Signup passed fine for days. Dormant bugs surface when a different code path finally runs.

Q54 What happens if bcrypt throws inside that hook?

The async function rejects. Mongoose sees the rejected promise, aborts the save, and save() itself rejects. In the controller the await throws, hits catch, goes to next(error), and lands in the error handler. Nothing is written to the database.

That's exactly right — a failed hash must never become a saved user.

Q55 Where does timestamps: true go?

In the second argument to the Schema constructor:

new mongoose.Schema({ /* fields */ }, { timestamps: true })

Put it in the fields object and Mongoose reads it as a field named timestamps whose type is true — which isn't a type. Hence Invalid schema configuration: 'true' is not a valid type at path 'timestamps'. It adds createdAt and updatedAt and maintains them for you.

Q56 required: true vs required: [true, "message"]?

The array form is [condition, message]. With bare true you get Mongoose's default — Path `email` is required. — accurate but developer-flavoured and not something you want reaching a user.

The array form lets you write the user-facing wording once, in the model, so every route that creates a user produces the same message.

Q57 What is validate and when do you use it?

A custom rule beyond the built-ins. validator returns true/false, and message can be a string or a function receiving props so you can include the offending value.

validate: {
  validator: v => /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9]).{8,}$/.test(v),
  message: "Password needs upper, lower, a number and a symbol"
}

Q58 Any caveat with a validator on a hashed field?

Yes. Validators run on the value being saved. Because hashing happens in a pre-save hook — which runs after validation — the strength regex correctly sees the plain password. But if you ever assign an already-hashed value directly, the regex would run against the hash. Worth knowing before it bites.

Q59 How does an error thrown inside a schema method reach your error handler?

Nothing magic happens. The method returns a promise; the controller awaits it; the rejection becomes a thrown exception at the await; catch calls next(error); Express routes anything passed to next to the four-argument error middleware.

In Express 5 you don't even need the try/catch — a rejected promise returned from a handler is forwarded automatically.

Q60 Why doesn't unique: true produce a nice Mongoose validation error?

Because unique is not a validator — it's an instruction to build a unique index in MongoDB. The rejection comes from the database, as error code 11000, after all validators have already passed.

That's why the error handler needs a separate 11000 branch that reads error.keyValue and returns a 409.

7. Indexes

Q61 What is an index?

A separate sorted structure — a B-tree — mapping field values to document locations. Without one, MongoDB does a collection scan and reads every document. With one, it jumps straight to the range it needs.

Q62 What does an index cost?

Disk space, and slower writes — every insert, update and delete must also update every index touching those fields. So you index what you actually query, not everything. An unused index is pure cost.

Q63 What types should you be able to name?

  • Single field — one field
  • Compound — several fields; order matters
  • Unique — rejects duplicate values
  • Text — word search across string fields
  • TTL — auto-deletes documents after a time; ideal for sessions, OTPs, password-reset tokens
  • Partial / sparse — indexes only documents matching a filter

Q64 What does { owner: 1, createdAt: -1 } mean?

It's a compound index. owner and createdAt are field names; 1 and -1 are sort direction — ascending and descending. It exists to serve one query shape:

Product.find({ owner: req.user._id }).sort({ createdAt: -1 })
// "this user's products, newest first"

(createdAt comes free from timestamps: true.)

Q65 Why does owner come first?

Field order follows the query: equality first, then sort or range. You filter by owner (equality), then sort by date.

With owner first, all of one owner's entries sit together in the index and are already ordered by date — MongoDB reads one contiguous slice and it's done. Reversed, the entries for a single owner are scattered and it has to jump around.

Q66 Does the direction actually matter?

For this query, no. MongoDB can walk an index backwards, so { owner: 1, createdAt: 1 } serves it just as well.

Direction only matters when a single sort mixes directions — .sort({ owner: 1, createdAt: -1 }) needs the index directions to match, or be exactly inverted. The part that always matters is field order.

Q67 What is the index prefix rule?

A compound index also serves queries that use a left-hand prefix of its fields. Given { a: 1, b: 1, c: 1 }, it supports queries on a, on a + b, and on a + b + c — but not on b alone or c alone.

Which is why you don't need a separate single-field index on a. Good thing to say unprompted; it shows you've thought about index count, not just index existence.

8. Express & Error Handling

Q68 What is middleware?

A function with the signature (req, res, next) sitting in the request pipeline. It can read or modify req/res, end the response itself, or call next() to pass control along. Registration order is execution order.

Q69 Why does the order matter in your app.js?

  • cors first — preflights must be answered before anything else runs
  • body parsers before controllers that read req.body
  • cookieParser before anything reading req.cookies
  • routes
  • 404 handler — reached only when no route matched
  • error handler — last of all

Q70 What makes a function an error middleware?

Four parameters: (err, req, res, next). Express inspects fn.length — three means normal middleware, four means error handler.

Classic bug Delete the unused next parameter to tidy up, and the function silently stops being an error handler. Errors then fall through to Express's default HTML error page.

Q71 Explain Promise.resolve(fn(req,res,next)).catch(next).

That's the asyncHandler wrapper, and it exists because in Express 4 a rejected promise inside a route was simply ignored — the request hung until it timed out.

  • fn(req,res,next) — call the handler; since it's async it returns a promise
  • Promise.resolve(...) — normalise it, so a handler that returns a non-promise still works
  • .catch(next) — any rejection is passed to next, which routes it into the error pipeline

Q72 Express 5 forwards async errors itself. Is asyncHandler dead?

For the plain "the handler rejected" case, yes — Express 5 wraps handler invocation and routes rejections to next for you.

You still write try/catch when you want to reshape an error — turning a raw TokenExpiredError into a 401 with code: "TOKEN_EXPIRED". That's precisely what the auth middleware and refresh controller do.

Q73 What can Express 5 still not catch?

Anything that escapes the request's call stack:

  • a throw inside a setTimeout / setInterval callback
  • a throw inside an event-emitter listener
  • a promise created but never returned or awaited (a floating promise)
  • a throw after the response has already been sent

By the time those fire, Express has no reference to the request any more. That's what the process.on handlers are for.

Q74 What do uncaughtException and unhandledRejection do?

They're the last safety net. uncaughtException fires for a synchronous throw nobody caught; unhandledRejection for a promise that rejected with no handler.

You use them to log and exit — not to keep running. After an uncaught exception the process state is unknown, so continuing risks corrupting data. Log it, exit non-zero, let a process manager (pm2, Docker, systemd) restart a clean process.

Q75 If Express auto-catches, why keep try/catch at all?

Three reasons: to translate a library error into your API's shape, to add context, and to run cleanup. Auto-forwarding gives you a generic 500. try/catch gives you a 401 with a code the frontend can act on.

Q76 Why does your error handler branch on error.name?

Because different sources throw differently shaped errors, and each maps to a different HTTP status:

  • ValidationError — Mongoose, holds an errors object of every failed field → 400
  • CastError — a malformed ObjectId, e.g. /products/not-an-id → 400
  • code === 11000 — duplicate key, from MongoDB itself → 409
  • anything else — statusCode if it's ours, otherwise 500

Q77 Why check typeof error.code === "string" before adding it to the payload?

Because Mongo's duplicate-key code is the number 11000, while our own codes are strings like TOKEN_EXPIRED. Without the check, the client would receive code: 11000 and might try to branch on it. The type check keeps the field meaning exactly one thing.

Q78 Why hide the message on a 500 in production?

Raw errors leak internals — file paths, query text, driver versions, sometimes credentials. Show users a generic message; log the real one server-side. Non-500 messages are ones you wrote deliberately, so those are safe to show.

Q79 Why is the 404 handler a path-less app.use?

If no route matched, execution reaches it — so a path-less app.use after all routes catches everything left. It must sit after the routes but before the error handler.

Express 5 change The bare '*' wildcard now throws. Use a path-less app.use, or '/*splat' if you need a named parameter.

9. Promises & async/await

Asked in almost every JS interview, and the follow-ups go deep.

Q80 What is a Promise, in one sentence?

An object that stands in for a value that isn't ready yet.

You get it instead of the answer, immediately, so your program can carry on instead of blocking. Later it either holds the answer or the reason there isn't one.

Q81 What are its states?

pending → then either fulfilled (with a value) or rejected (with a reason). Once it settles it never changes again — a one-way door. That's why attaching .then to an already-settled promise still fires.

Q82 Is Promise a built-in? A class?

Both. Promise has been a built-in class in the language since ES2015, constructed with new Promise((resolve, reject) => { ... }). Before that, libraries like Bluebird and jQuery deferreds provided their own.

Q83 How does a promise get produced?

Something starts work that can't finish now — a network call, a file read, a timer — and immediately hands back a pending promise. The actual work is handed to the environment (the OS, the browser, libuv in Node).

When that work completes, the runtime calls resolve or reject, which settles the promise and queues its callbacks onto the microtask queue.

Q84 What is async/await really?

Syntax over promises. async makes a function always return a promise. await pauses that function until a promise settles, then gives you the value — or throws the rejection reason.

Nothing new is happening underneath. It just lets asynchronous code read top-to-bottom like synchronous code.

Q85 So .then and await are the same thing?

Two ways to consume the same promise. .then takes a callback; await suspends the enclosing function. await is usually clearer, especially for sequences and for error handling.

.then still earns its place for fire-and-forget chains, for .finally cleanup, and in places where you can't use await — like the shared refreshPromise, where you want to hold the promise rather than wait on it.

Q86 Then what is try/catch's role?

try/catch is the language's general exception handler — nothing to do with promises specifically. It works with await because await converts a rejection into a thrown exception.

The consequence Without await, a rejected promise doesn't throw, and try/catch sees nothing at all. A missing await silently disables your error handling.

Q87 What is a "thenable"?

Any object with a callable .then(resolve, reject) method. The promise machinery never checks instanceof Promise — it duck-types for a .then. If it finds one, it calls it and adopts the result.

That's how non-native promise libraries interoperate with await: await works on any thenable, not just real promises.

Q88 Is getUser(1).then() a thenable?

No — that's calling .then on something. The thenable is getUser(1), the object that has the method.

And .then() with no arguments is a no-op pass-through: it returns a new promise with the same outcome as the original.

Q89 What did we have before async/await?

Callbacks. You passed a function to be run "when it's done", so error handling was an if (err) at the top of every one, and sequencing meant nesting — callback hell. Promises (ES2015) flattened the nesting into a chain; async/await (ES2017) made the chain look like ordinary sequential code.

Q90 Back then, how did you know a function was asynchronous?

You didn't, from the signature alone — it was convention plus documentation. The Node convention was error-first callbacks: fn(args, (err, result) => {}). If a function took a callback last and returned nothing, you assumed async.

That's a real argument for promises: the function now returns something you can inspect, so asynchrony is visible in the code rather than implied by a naming convention.

Q91 What is Promise.reject(error), and why does it need a return?

Promise.reject(x) creates an already-rejected promise. In an interceptor you return it to say "this request failed — propagate the failure to whoever called."

if (!shouldRefresh) {
  return Promise.reject(error);   // the return is load-bearing
}

Without return, the promise is created and discarded, execution falls through to the code below, and the interceptor ends up returning undefined. The caller's await then resolves with undefined instead of throwing — a very quiet bug that turns a failed request into a successful one.

Q92 Where do promise callbacks run?

The microtask queue, which is drained after the current synchronous code finishes and before the next macrotask (timers, I/O). That's why a .then fires before a setTimeout(fn, 0) registered earlier.

setTimeout(() => console.log("timeout"), 0);
Promise.resolve().then(() => console.log("promise"));
console.log("sync");
// sync → promise → timeout

10. React & Next.js

Q93 What is Context and when should you use it?

A way to pass a value to any depth of the tree without threading props through every level. Use it for genuinely app-wide things — the logged-in user, theme, locale.

Don't use it for values that change rapidly: every consumer re-renders when the value changes, so a fast-changing context is a performance problem disguised as convenience.

Q94 React 19 changed the provider syntax — what changed?

You render the context object directly:

<UserContext value={{ user, logout }}>{children}</UserContext>

<UserContext.Provider> still works but is deprecated. Consuming is unchanged: useContext(UserContext).

Q95 Why does useUserContext throw when the context is null?

Because the default value is null, so reading it outside the provider gives you null. Throwing converts a confusing "cannot read property of null" deep inside some component into a clear message at the point of misuse.

It also narrows the type — after the throw, TypeScript knows the value isn't null, so consumers stop getting "possibly null" errors on every property.

Q96 When you call a state setter, does the variable update immediately?

No. The variable in the current render is a const captured for that render. The setter schedules a re-render; the new value appears in the next render's variable. Reading it on the line after the setter gives you the old value.

Q97 Why does the updater form setX(prev => ...) exist?

Because the value you closed over may be stale. If two updates queue in the same tick, setCount(count + 1) twice both read the same count, so you increment once.

setCount(count + 1);        // both read the same captured value
setCount(count + 1);        // net effect: +1

setCount(prev => prev + 1); // each receives the latest queued value
setCount(prev => prev + 1); // net effect: +2

Rule: use the updater form whenever the new state depends on the old one.

Q98 Why key={item._id} and not key={index}?

Keys tell React which element is which between renders. With a filtered or reordered list, index keys shift — React reuses the wrong DOM node, and component state lands on the wrong row.

A stable ID from the server survives reordering. This showed up concretely as delete-in-progress state attaching to the wrong item after a deletion.

Q99 When do useMemo / useCallback actually help?

  • useMemo — when a computation is genuinely expensive, or when an object/array identity must stay stable because something depends on it.
  • useCallback — when a function is passed to a memoized child, or used as an effect dependency.

If neither applies they cost more than they save: they run on every render and hold memory. "I wrap everything in useCallback" is a wrong answer.

Q100 Why fetch /me on mount instead of trusting client state?

The tokens live in httpOnly cookies, invisible to JavaScript, and React state is wiped on every reload. /me is the only way to answer "who am I?" after a refresh.

It also revalidates server-side — the session might have been revoked since the tab was opened.

Q101 Why does the login page flash before redirecting a logged-in user?

Because the redirect lives in useEffect, which runs after the first paint. The component renders, the browser paints it, then the effect fires and navigates. The user sees the login form for a frame or two.

Q102 How do you fix the flash properly?

Don't render the page until you know who the user is. In this app UserProvider renders a skeleton until /me answers, so children never render in the unknown state — the login page can't flash because it hasn't mounted yet.

The stronger answer: decide on the server, so the wrong page is never sent at all.

Q103 What is proxy.ts, and why didn't you use it for the auth guard?

It's Next's edge middleware, renamed from middleware.ts to proxy.ts in Next 16. It runs before the request reaches a route, so it can redirect with zero flash.

I didn't use it here because at the edge it can only see whether a cookie is present, not whether the JWT is valid — verifying would need an edge-compatible JWT check or a network call. Presence-only is a legitimate first pass for UX, with the real authorization still enforced on the API. It should never be your only check.

Q104 Server vs client components — when do you need "use client"?

Client components are required for state, effects, event handlers, browser APIs, and context providers. Everything else is better as a server component: no JavaScript shipped to the browser, and data fetching happens closer to the source.

"use client" marks a boundary — everything imported below it becomes client code too, so put it as low in the tree as you can.

Q105 Why is UserProvider in the layout rather than in a page?

The layout persists across navigation, so the session is fetched once. In a page it would refetch and lose state on every route change.

Q106 Why router.replace and not router.push in a redirect guard?

push adds a history entry, so the back button returns to the login page they were just bounced off — and bounces them again. replace swaps the current entry, so back goes where they actually came from.

11. axios & the Interceptor

Q107 What is an interceptor?

A hook axios runs on every request or response before your code sees it. A response interceptor takes two functions — one for success, one for errors — mirroring .then(onSuccess, onError).

Q108 What does (response) => response do?

Nothing — it's the identity pass-through for the success case. You have to supply it because the error handler is the second argument.

You could return response.data.data here to unwrap the API envelope globally, but then every call site's type changes and you lose access to status and headers. Usually not worth it.

Q109 What is original?

error.config — the complete configuration of the request that failed: url, method, headers, data, everything. Passing it back into api(original) re-sends exactly the same request. That's the mechanism that lets a request survive a token refresh transparently.

Q110 Why api(original) and not axios(original)?

api is the configured instance — baseURL, withCredentials, and the interceptors. axios(original) would bypass all of that.

Note the inverse for the refresh call itself: it deliberately uses bare axios, so that a failing refresh doesn't re-enter the interceptor and recurse.

Q111 Several requests 401 at the same moment. What happens?

They all reach the interceptor, all find refreshPromise already set, and all await that same promise. One network refresh happens; then each replays its own original request. Without the shared promise, concurrent refreshes plus rotation would invalidate one another and log the user out.

Q112 Why redirect with window.location.href instead of the Next router?

The interceptor isn't a component, so no hooks are available. A hard navigation also wipes all in-memory state, which is what you want after a session dies.

The typeof window !== "undefined" guard is because this module can be evaluated during server rendering, where window doesn't exist.

Typo that cost me an hour typeof window !== undefined — without the quotes — is always true, because typeof returns a string and a string is never the undefined value.

Q113 Why check onAuthPage before redirecting?

If the failure happened while already on /login, redirecting to /login reloads the page, which runs /me again, which fails again — a reload loop. Skip the redirect when you're already where you'd be sending them.

12. TypeScript

Q114 What is React.Dispatch<React.SetStateAction<T>>?

The type of a useState setter, built from two pieces:

  • SetStateAction<T> = T | ((prev: T) => T) — a value or an updater function
  • Dispatch<A> = (value: A) => void

Together: "a function accepting either a new value or an updater, returning nothing." Note the order — Dispatch wraps SetStateAction, not the reverse.

Q115 Why is a caught error typed unknown?

Because JavaScript lets you throw anything — a string, a number, null. TypeScript refuses to assume it's an Error. You narrow before using it:

catch (error) {
  if (axios.isAxiosError<{ message?: string }>(error)) {
    toast.error(error.response?.data?.message ?? "Request failed");
  } else if (error instanceof Error) {
    toast.error(error.message);
  }
}

isAxiosError is a type guard — it narrows the type and tells TS that error.response exists.

Q116 string vs String?

string is the primitive type — what you always want. String is the wrapper object type. A string is assignable to a String but not the reverse, which produces confusing errors like Type '"" | String' is not assignable to type 'string'. Same for number/Number and boolean/Boolean.

Q117 Why "Property 'data' does not exist on type 'never'"?

Because the value was narrowed all the way to never — usually a caught error typed unknown that you tried to use without narrowing first, or an exhaustive check that eliminated every remaining possibility. Narrow with a type guard before touching properties.

Q118 Why does indexing an object with a plain string fail?

obj[key] where key: string asks TypeScript to allow any string, but the type only declares specific keys. Fix by typing the key as keyof User, or by iterating with Object.entries(obj), which hands you correctly typed pairs.

Q119 What does interface Task extends FormValues { _id: string } give you?

Everything in FormValues, plus _id. It's the standard answer to "the form shape, plus what the server adds" — you declare the shared fields once and the two types can't drift apart.

13. War Stories

The strongest interview material in this document. A specific bug, a wrong first hypothesis, and how the evidence corrected it — that's what separates you from someone who has only read about these topics.

1 The infinite refresh loop

Symptom: the login page reloaded forever.

First hypothesis (wrong): the NO_TOKEN code was being treated as refreshable.

What disproved it: removing that branch changed nothing. So the cause had to be state surviving across reloads — which narrowed it to the cookies.

Real cause: the refresh controller returned 401 but never cleared the cookies, so every reload replayed the identical doomed cycle.

Lesson: a failure must leave the client in a changed state, or retrying is guaranteed to repeat.

2 select: false didn't hide the password

It applies to queries only. User.create() doesn't query — it returns the document you just built. Fixed with a toJSON transform, which covers every path out.

Lesson: query-time options don't govern non-query paths. Put the guarantee at the layer everything passes through.

3 The async hook that called next()

Signup worked for days. Login crashed with TypeError: next is not a function — because login triggers a second save (to store the refresh token), and only that path reached the branch containing next().

Lesson: dormant bugs surface when a different code path finally runs. "It worked yesterday" often means "yesterday I didn't run that line."

4 "Could not reach server" blamed on CORS

The preflight was fine. The dev server was restarting mid-request, because node --watch was watching a directory that had temporary files being written into it. In-flight requests were killed by the restart.

Lesson: confirm the server is alive and stable before debugging the protocol. Check the process before you check the headers.

5 The cookie that was too short-lived

Setting the access cookie's maxAge to the access token's lifetime meant the browser dropped the cookie the instant the token expired. So jwt.verify never ran, TokenExpiredError never fired, and the refresh flow could never trigger.

Lesson: a security control tuned too tight can disable the very mechanism that depends on it. Two expiry clocks for one concept is one clock too many.
